# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Hôtel Evasion**, a hotel in Côte d'Ivoire (Bouaké, per the sibling asset folder — not yet confirmed with the client), built on Laravel 12. The app has **two independent halves**:

1. **Public marketing site** — fully static Blade/Bootstrap pages (no database involvement at all). Styled with the "Luxivo" Bootstrap 5 HTML template originally supplied at `../EspaceKatioka-Gestion-hotel/`.
2. **Hotel management back-office** (`/admin`) — real, database-backed staff tooling: room inventory & availability, guest records, reservations/stays, invoicing & payments. Staff-only; there is no public-facing account system or online booking integration — the public site's booking/contact forms remain decorative by design (see below).

These two halves don't share data or templates. The public site was originally converted from a previous Laravel build for a different client (a dental clinic) by stripping all Filament/DB code down to a static site; the management back-office was then added on top of that static site, reintroducing PostgreSQL and a full data model — **first with a Filament v4 admin panel, then rebuilt as a bespoke Blade + vanilla-JS interface** at the client's explicit request ("Blade et JS... il faut pouvoir affecter les chambres à des clients"). Filament was fully removed in that rebuild; don't reintroduce it without checking with the client first — the whole `/admin` UI is now hand-rolled controllers/views, on purpose.

**Public site content** — rooms, services and the home page texts/photos come from the application (see below); what's left of the template's sample data (home contact block) is translated from the original English template. The hotel's own contact details (name, phones, e-mail, address, social links) are **not** placeholders any more: they come from Configuration → Hôtel (see "Hotel information" below), and are simply hidden while empty. Room/guest/reservation data in the admin is real, staff-entered data (seeded with demo room types/rooms only to avoid an empty first login).

## Structure: two distinct halves (website / application)

Since 2026-10-10 the code is split so the public **website** and the management **application** never mix — keep it that way:

| | Website (public) | Application (staff) |
|---|---|---|
| Routes | `routes/site.php` (loaded as the `web` file) | `routes/admin.php` (loaded in `then:`) |
| Controllers / requests | `App\Http\Controllers\Site\…`, `App\Http\Requests\Site\…` | `…\Controllers\Admin\…`, `…\Requests\Admin\…` |
| Views | `resources/views/site/` (`layouts/app`, `partials/header|footer`, `pages/`, `demande/`, `components/` → `<x-site::…>`) | `resources/views/admin/` (`components/` → `<x-admin::…>`) |
| Public files | `public/site/` (the Luxivo template — css, fonts, images, js — + `demande.css/js`) | `public/app/` (`css/admin.css`, `js/admin.js`, `images/`) — **not** `public/admin/`: a real folder named like the `/admin` route prefix makes the web server serve the folder (404 on `/admin`) instead of Laravel |
| Tests | `tests/Feature/Site/` | `tests/Feature/Admin/` |

Shared: `public/vendor/` (Bootstrap 5.3 css/js + popper, Font Awesome 5 Pro — the application's own copies, so it no longer depends on the template's files), models, `App\Support\*`, `resources/views/errors/` (extend the site layout; 403 the admin one). The component namespaces are registered in `AppServiceProvider` (`Blade::anonymousComponentPath(…, 'site' | 'admin')`). **The site only reads what the application publishes** (rooms marked published, hotel info, prices); `/demande` (and later the contact form) is the only place it writes.

**Addresses** (`config/routing.php`): with `SITE_DOMAIN` / `ADMIN_DOMAIN` empty (today, no domain yet) one address serves both — site at `/`, application under `/admin` (`routing.admin_prefix`). Setting both gives each half its own host (`Route::domain(...)` wraps each routes file): the application then answers at the **root** of its host, and each host 404s the other half's pages (`SubDomainRoutingTest`). In production, list both hosts in `SERVER_NAME` for Caddy's HTTPS. The application is `noindex` (meta tag) and `/admin` + `/demande/suivi` are disallowed in `public/robots.txt`.

The template pages without real content were **removed** (À propos, Équipe, Offres, Tarifs, FAQ, Blog, service detail); kept: Accueil, Chambres (+ détail), Services, Galerie, Contact, `/demande`. Their content is to be managed from the application (steps in progress).

**Rooms on the website (done)**: `Site\RoomController` — `/chambres` lists `Room::published()` rooms (ticked « Afficher sur le site » **and** of an active type), sorted by type then natural number, with type filter tabs (template Isotope grid); `/chambres/{room}/{slug}` (`Room::publicUrl()`, wrong/missing slug → 301, unpublished → 404) shows the presentation (escaped; description paragraphs via `nl2br(e())`), all offered formulas with their window and price (`Room::publicRates()`, `lowestRate()` for « dès … »), amenities, features, rules, cancellation policy, photos (cover = first `RoomImage`, others in a grid; no photo → neutral `.room-photo-placeholder`, never a stock picture), and a « Libre en ce moment » badge when `isAvailableNow()`. The home page (`Site\HomeController`) shows up to 6 published rooms and hides the section when there are none. `<x-site::room-card :room>` renders a card; its photo must **not** be `loading="lazy"` (the template's Isotope waits for images) and `site.css` crops card photos to 4:5 (the overlay card needs a tall picture). Our own site styles live in `public/site/css/site.css` (template files untouched). In the application, published rooms get a « Publiée » badge (room list) and a « Voir sur le site » button (room page).

**Home page & services managed from the application (done)** — section **« Site web »** of the sidebar (simple mode: « Plus »), permission `site.manage` (Gérant via the system role). Migration `2026_10_11_100000_*`:
- `SiteContent` (`site_contents` key/value table) — home texts (`hero_title`, `hero_text`, `about_*`, `about_highlights` one per line, `stat_{1..4}_value/_label`, `testimonial_{1..6}_name/_role/_text`) and photos (`SiteContent::PHOTOS`, stored under `site/` on the public disk, the old file deleted on replace/remove). `HomeContentController` (`/admin/site/accueil`, `SiteHomeRequest`). Read once per request through a container instance (`values()`, `get()`, `photoUrl()`, `stats()`/`testimonials()` return only *complete* entries, `highlights()`); `store()` flushes it. **An empty value shows nothing — never sample content**: hero title defaults to « Bienvenue à {nom} », the hero background to the stock `hero-bg.jpg`; À propos (needs `about_text`), key figures, testimonials (initials avatar, no stock photo) are hidden when empty. With only one À propos photo the template's 400 px badge gets `.site-about--single`.
- `Service` (`services` table: title, category, description, FA5 `icon` from `Service::ICONS`, `photo` in `site/services/`, `position`, `is_published`, `show_on_home`) — CRUD `Admin\Site\ServiceController` (`/admin/site/services`, `ServiceRequest`; deleting removes the photo). On the site: `/services` (`Site\ServiceController`) shows published services ordered by position — without photo as `<x-site::service-card>` tiles, with photo as the template's large numbered cards, an empty-state notice when none; the home page shows up to 6 `show_on_home` ones (`HomeController`) and hides the section otherwise.

Limits: `MAX_PER_UPLOAD` 10, `MAX_TOTAL` 60 (`GalleryUploadRequest::after()`), real images only (jpg/png/webp ≤ 2 MB, ≥ 300×200). Site: `/galerie` (`Site\GalleryController`) shows published photos in order, 4:3 crops, Magnific popup, captions, Isotope filter tabs when there are ≥ 2 categories (`GalleryPhoto::categoryFilter()` / `categoriesOf()`), an empty-state notice otherwise. The photo strip `site/partials/photo-strip` (home + gallery, last 10 published, hidden when empty) is titled « Suivez-nous sur Instagram » linking to `hotel.info.instagram` only when set, else « Quelques images de l'hôtel ». Room photos are deliberately not mixed into the gallery.
- `SiteEvent` (`site_events`, migration `2026_10_11_400000_*`: title, `starts_at`, optional `ends_at`, location, description, `photo` poster in `site/events/`, `price_label`, `booking_info` = link / phone / short text, `is_published`; `visible_until` derived on save = `ends_at` or the end of the start day) — CRUD `Admin\Site\EventController` (`/admin/site/evenements`, `SiteEventRequest`: end after start, `www.` gets `https://`, `javascript:`/`data:` refused; upcoming vs past lists). `scopeUpcoming()` (published, `visible_until >= now`, soonest first) is the only website query: past events leave the site by themselves, no cron. Site: the **next event sits inside the home banner** under its button (`.site-event-bar`, « Prochain événement » / « En ce moment ») so it's seen on arrival whatever the screen height — an earlier version under the hero fell below the fold on 1366×768; a « Événements à venir » section shows the next 3 (`<x-site::event-card>`), `/evenements` (`Site\EventController`) lists them all with full description and booking link (`bookingLink()`: https → link, phone → `tel:`, else text); the « Événements » menu item and both home blocks only exist while there are upcoming events.
- **Website audience (« Site web → Statistiques », permission `site.stats`)** — `App\Http\Middleware\RecordSiteVisit` wraps the whole `routes/site.php` group and inserts one `SiteVisit` row (`site_visits`, migration `2026_10_11_500000_*`) per real page view: GET, 200, `text/html`, not ajax/prefetch, not a logged-in user, not a bot (`SiteVisit::isBot()` — crawlers, WhatsApp/Facebook link previews, curl, headless browsers…); any failure is logged and never breaks the page. **No cookie, no IP stored**: `visitor` = sha256(day + IP + user agent + app key), so a person is one visitor per day and can't be followed across days; `is_entry` marks a visitor's first page of the day = one **visit**, which carries the `source` (Referer classified by `SiteVisit::sourceOf()`: direct, google, other search engines, facebook, instagram, whatsapp, tiktok, x, other + host; a link from the site itself counts as direct) and `device` (mobile/tablet/desktop from the UA). `label` is the page name (`SiteVisit::PAGES`, « Chambre : {displayName} » for room pages; `/demande` = « Demande sur place (QR code) », the QR code being its only entry point). `App\Support\SiteStats` (calendar days, app timezone) feeds `Admin\Site\SiteStatsController` (`/admin/site/statistiques`): today / this month / this year tiles vs the same span before, a column chart for `?periode=jours|mois|annees` (30 days, 12 months, every year since the first visit; inline SVG like the dashboard, with a data table), sources + referrer hosts, devices, top pages (views and distinct visitors), and conversions (online booking requests and how many became réservations, QR requests and how many were validated, page views of both forms). Behind a reverse proxy the real client IP comes from `trustProxies(at: '*')`. Rows are never pruned yet.
- The template's decorative search bar on the home page is replaced by a « Nous contacter » CTA; its fictive « facilities/features » blocks are gone. The home page contact block is still template content (contact step to come). The home banner's template overlay (96 % opaque) is lightened in `site.css`.

## Commands

Setup:
```bash
composer install
cp .env.example .env   # if .env doesn't already exist
php artisan key:generate
php artisan migrate --seed
php artisan storage:link   # room photos are served from public/storage
```
(`composer setup` runs the same steps but uses `migrate --force` **without** `--seed`, so it leaves you with no admin user — run `php artisan db:seed` afterwards.)

Local development:
```bash
composer dev   # php artisan serve + php artisan pail (log tailing)
```
`composer dev` launches both via `npx concurrently`, so it needs Node/npx on the PATH even though the project has no `package.json` (npx fetches `concurrently` on the fly).

There is **no frontend build step anywhere in this app** — Tailwind/Vite were removed along with the original dental-clinic code and never reintroduced. The public site's assets are static files under `public/site/` (copied verbatim from the Luxivo template). The admin's assets are also static/hand-written: `public/app/css/admin.css` and `public/app/js/admin.js`, reusing the same Bootstrap 5 / Font Awesome files already vendored under `public/site/` — no separate CSS framework, no npm dependency for the admin either. `admin.css` is a small design system: brand tokens on `:root` (`--ek-primary` navy derived from the sidebar's `--ek-sidebar-from`/`--ek-sidebar-to` gradient, `--ek-gold` accent, blue-gray neutrals; status colors stay semantic — green = disponible, etc.), Bootstrap's own `--bs-*` variables re-pointed at them (so `btn-primary`, `bg-success` badges, pills, pagination, focus rings follow the theme), and soft-tinted status badges. Fonts are Plus Jakarta Sans + Gilda Display from Google Fonts (same as the public site), with system-font fallbacks. **Font Awesome is the vendored 5.14 Pro** — use FA5 icon names (`fa-tachometer-alt`, `fa-calendar-alt`, `fa-th-large`…); FA6 names (`fa-gauge`, `fa-calendar-days`, `fa-grid-2`) render as empty squares.

Run tests:
```bash
php artisan test            # or `composer test` (clears config cache first)
php artisan test --filter=testMethodName
```

Lint/format PHP:

```bash
vendor/bin/pint
```

### Docker (dev + production) — see `DOCKER.md` (French, for the client)

Two services: `app` = **FrankenPHP** image (Caddy + PHP 8.2 in one process, `Dockerfile` targets `prod`/`dev`, non-root `appuser`, extensions pdo_pgsql/bcmath/intl/exif/gd/zip/opcache) and `db` = `postgres:16-alpine` (not published in prod). `compose.yaml` = production (VPS): `env_file: .env.production` (template `.env.production.example`; **the `POSTGRES_*` vars are the single source** — `docker/entrypoint.sh` maps them to `DB_*`), volumes `storage` (→ `/app/storage`: photos, logo, sessions), `db_data`, `caddy_data`/`caddy_config`. `SERVER_NAME=":80"` = plain HTTP on the VPS IP; setting a domain there switches Caddy to automatic Let's Encrypt HTTPS (`docker/Caddyfile`: security headers, no `Server`/`X-Powered-By`, 10 MB body, static caching). `compose.dev.yaml` = development: code bind-mounted, http://localhost:8080, Postgres on 5433 (katioka/katioka), APP_KEY read from the local `.env`. The entrypoint refuses to start prod without `APP_KEY`, waits for Postgres, recreates the **relative** `public/storage` symlink (also the host's now — an absolute one breaks inside containers), runs `migrate --force` (disable with `RUN_MIGRATIONS=false`), then `optimize` (prod) / `optimize:clear` (dev). `.dockerignore` keeps `.env*`, `vendor`, `storage/backups`, uploads, tests out of the image. **Fresh production database: never `db:seed`** (weak demo admin + sample rooms). The entrypoint runs **`php artisan hotel:ensure-admin`** after migrating (`App\Console\Commands\EnsureAdminAccount`): **only when the `users` table is empty** it creates a Gérant from `ADMIN_EMAIL` (default `admin@espace-katioka.local`) / `ADMIN_PASSWORD` (read with `getenv()` so a cached config can't hide them; validated against `Password::defaults()`, refused if under 4 characters) or, without a password, a random 16-char letters+digits one printed once in the container logs — always with `must_change_password = true`; any existing account ⇒ it does nothing, ever (failure doesn't stop the container). Other managers / forgotten passwords: **`php artisan hotel:create-manager`** (`App\Console\Commands\CreateManagerAccount`: interactive or `email --name --password`, `Password::defaults()`, Gérant role, also resets an existing account and logs it out everywhere).

**`phpunit.xml` forces its test environment** (`force="true"` on both `<env>` and `<server>` for APP_ENV, DB_*, CACHE_STORE, SESSION_DRIVER, QUEUE_CONNECTION, MAIL_MAILER, and empty ADMIN_EMAIL/ADMIN_PASSWORD so a local `.env` can't leak into the default-admin tests): in a container those are real environment variables, which PHPUnit otherwise doesn't override — tests then hit the container's PostgreSQL and run with APP_ENV=local (CSRF 419s). Keep the `force` attributes.

### Database is PostgreSQL — a local connection quirk

`DB_CONNECTION=pgsql`. In this development environment, TCP connections to `127.0.0.1`/`localhost` hang indefinitely — not fail, **hang** — during libpq's GSSAPI encryption negotiation. Two ways around it, in case a fresh shell hits this again:
- Prefix ad hoc `php artisan`/`psql` invocations with `PGGSSENCMODE=disable` (e.g. `PGGSSENCMODE=disable php artisan migrate`).
- Or point `DB_HOST` at the Postgres Unix socket directory (e.g. `/tmp` for a Homebrew install) instead of a TCP host — sockets aren't affected since there's no GSSAPI negotiation over a Unix socket.

This is a local/sandbox networking quirk, not an application bug — don't "fix" it by disabling GSS encmode inside app config; it's a per-shell workaround only. `tests/` are unaffected: `phpunit.xml` forces `DB_CONNECTION=sqlite` / `DB_DATABASE=:memory:` for the test environment regardless of the app's runtime DB, so `php artisan test` never touches Postgres or this issue.

## Architecture — public site (static half)

**Routing** (`routes/site.php`) — every public page is a `Route::view(...)` call straight to a Blade view; no controller layer, no dynamic data. "Detail" pages (`/chambres/detail`, `/services/detail`, `/equipe/detail`, `/offres/detail`, `/blog/detail`) are single static URLs showing one example item each — deliberately *not* wired to the real `Room`/`Guest`/etc. models from the admin half.

**Views** — `resources/views/site/layouts/app.blade.php` is the shared layout (head, preloader, header include, `@yield('content')`, footer include, scripts). `resources/views/site/partials/header.blade.php` / `footer.blade.php` hold the nav/footer chrome (French, trimmed to pages that actually exist — the template's alternate homepages `index-2`/`index-3`, the `rooms-2` list layout, and `blog-standard` were not ported). `resources/views/site/components/page-hero.blade.php` is the inner-page title/breadcrumb banner. `resources/views/site/components/room-card.blade.php` is the grid-style room card on `site/pages/chambres.blade.php`, looped over a hardcoded PHP array — **not** backed by the admin's `Room` model.

**Styling is Bootstrap 5, not Tailwind** — loaded as a fully separate, self-contained asset bundle (`public/site/css/style.css` + plugin CSS/JS, jQuery, Bootstrap JS bundle, Slick/Isotope/AOS/Magnific Popup/Nice Select).

**Public forms are decorative** — the search bar, booking widget, contact form, newsletter signup, and comment forms render but have no backend wiring (no `Mail::send`, no DB row, no relation to the real `Reservation`/`Guest` models). This was a deliberate scope decision (no public booking flow yet), not an oversight.

**Online booking requests (« Réserver », `/reservation`) are database-backed too** — the header button of the site (and « Réserver cette chambre » on a room page, `?type=` pre-selecting its type) leads to `Site\BookingRequestController@create`: room type cards (`BookingRequest::offeredRoomTypes()` = active types with ≥ 1 published room and ≥ 1 rate), formula cards (disabled when the type has no rate), arrival (date for a nuitée, date+time otherwise), duration, occupants, contact (**only the phone is required**), message; live estimate in `public/site/js/reservation.js` (display only; no `<select>` on purpose — the template's nice-select swallows native `change` events; scripts go through `@stack('scripts')` in the site layout). `BookingRequestRequest` refuses a past arrival or one more than a year ahead, a formula the type doesn't offer, a type with **no room free over the period** (`Room::availableBetween`, hors service excluded; neutral message), a second pending request from the same phone, the honeypot; `throttle:10,10`. A `BookingRequest` (`booking_requests`, migration `2026_10_11_300000_*`) **is not a reservation**: no invoice, no room held; rate/departure/total derived (indicative). Signed follow-up page `/reservation/suivi/{id}` (pending / « Réservation enregistrée » / refused + reason; disallowed in robots.txt). Application: **Réservations → Demandes en ligne** (`Admin\BookingRequestController`, `/admin/demandes-reservation`, tabs en attente / réservations créées / refusées, `reservations.view`; refuse with optional reason, `reservations.manage`; pending count badge in the sidebar, the simple nav and a banner on the réservations list). « Créer la réservation » opens the usual form with `?demande=ID` (`ReservationController@create` pre-fills mode, arrival, duration, occupants, notes, and the client — an existing guest matched by phone, else the new-client fields; the room `<select>` loads on page load and pre-selects a room of the requested type via `data-preferred-type`, using `room_type_id` from `/admin/rooms/available`); the hidden `booking_request_id` makes `ReservationController@store` lock the request and mark it `traitee` with `reservation_id`/`handled_by` in the same transaction (already handled ⇒ validation error, nothing created).

**One exception: `/demande` (guest room requests) is database-backed.** **It is never linked from the website** (client request, 2026-10-10): the header button is « Réserver » (online booking requests, below), footer/CTA buttons say « Nous contacter »; guests reach it only through the lobby QR code (or a direct address), and `robots.txt` disallows `/demande` — `PublicSmokeTest::test_no_site_page_links_the_room_request` guards this. A guest who has just arrived opens `/demande` on their phone (e.g. from a QR code in the lobby), picks a free room, a formula and a duration, optionally gives name/phone (**all optional**, client request — stored as empty strings, shown as « Client de passage » via `StayRequest::fullName()`, validated into a « Client de passage » guest; a phone, when given, must be valid and is limited to one pending request) and sends a request (`App\Http\Controllers\Site\StayRequestController` — the only public controller —, `App\Http\Requests\Site\StayRequestRequest`, views in `resources/views/site/demande/` with their own light layout + `public/site/css/demande.css` + `public/site/js/demande.js`, deliberately *not* the heavy Luxivo layout). No account: the follow-up page `/demande/suivi/{id}` is a **signed URL** (also kept in the session). The list only shows `Room::availableNow()` rooms of active types with at least one formula open now (rate set; nuitée only inside its window). Arrival = server time, rate = room type's, total/departure derived by the model — nothing price-related is read from input. Abuse guards: `throttle:10,10` on the POST, a honeypot field (`website`), one pending request per phone number, and errors that never reveal anything about other guests (an availability failure under lock is replaced by a generic message). Don't wire the decorative forms above to anything without asking — this page is the sanctioned public entry point.

## Architecture — hotel management back-office (`/admin`, custom Blade + JS)

Staff-only, session-based auth via a plain `App\Http\Controllers\Admin\AuthController` (`Auth::attempt` with `is_active => true`, throttled to 5 failures per e-mail+IP via `RateLimiter`; no public registration route — staff accounts are created by authorized staff in `/admin/users`, see **Staff accounts, roles & permissions** below). Routes live in **`routes/admin.php`**, not `routes/site.php` — it's loaded from `bootstrap/app.php` via `withRouting()`'s `then:` callback (`Route::middleware('web')->group(base_path('routes/admin.php'))`), keeping `routes/site.php` dedicated to the public site as documented above. Guests are redirected to `admin.login` via `$middleware->redirectGuestsTo(...)` in `bootstrap/app.php`.

**Data model** (`app/Models/`, migrations in `database/migrations/2026_08_03_2003*`) — unchanged since the Filament era, still the single source of truth:
- `RoomType` — "type de chambre" (unique name, slug auto-generated and collision-safe — no longer in the form, description, adult/child capacity, is_active) with **four optional rates**, one per pricing formula: `hourly_rate` (per hour), `day_rate` ("journée", a fixed block of `config('hotel.day_hours')` = 6 h, e.g. 08:00 → 14:00; added by migration `2026_10_08_100000_*`), `night_rate` ("nuitée", 22h00 → 12h00 next day) and `stay_rate` ("séjour", per period of at least 24 h). A null rate means that formula isn't offered for the type. The formula windows live in `config/hotel.php`. `night_rate` is the former `base_price` (renamed by migration `2026_10_07_300000_*`, values kept). **Reservations are still priced `nights × rate_per_night`**: only `night_rate` is used today, to pre-fill `rate_per_night` (board card `data-night-rate`, `night_rate` key in the `/admin/rooms/available` JSON) — hourly/stay pricing in reservations is a planned follow-up. Managed under the sidebar's "Configuration" section (`rooms.manage` permission).
- `Room` — physical unit (`room_type_id`, `number`, `floor`, `status` cast to the `App\Enums\RoomStatus` backed enum: disponible/occupee/nettoyage/hors_service).
- **Room public presentation** (what the website's room page — template at `/chambres/detail` — shows, entered in the back-office room form, section "Présentation sur le site web"): `is_published`, `public_name` (`Room::displayName()` falls back to the room type's name), `tagline`, `surface` (m²), `beds`, `bathrooms`, `description`, `amenities` (JSON, `AsEnumCollection` of `App\Enums\RoomAmenity` — label + FA5 icon), `features` and `rules` (JSON string lists, typed one per line in textareas and split/trimmed/deduplicated in `RoomRequest::prepareForValidation()` — an **empty** textarea arrives as `null` (ConvertEmptyStringsToNull) and is turned into `[]` there, otherwise the `array` rule rejects it), `cancellation_policy` (migration `2026_10_08_700000_*`). Capacity and price are **not** duplicated: they come from the room type. Like the photos it needs `rooms.manage` (`Room::PRESENTATION_FIELDS`; `RoomRequest::touchesPresentation()` + `RoomController::authorizeImages()`, checked before saving); the form posts a `presentation=1` marker so unticking every amenity clears them, and the Réception's form (rooms.edit) has no such fields, so saving a status leaves the presentation untouched. **The public site doesn't read these yet** — `/chambres/detail` is still the static template.
- `RoomImage` — room photos, **max 5 per room** (`RoomImage::MAX_PER_ROOM`, first by `position` = cover), files on the `public` disk under `rooms/{room_id}/` with random names, URL via `asset('storage/…')` (host-relative, independent of `APP_URL`) — **requires `php artisan storage:link`** (done locally; redo on every new deployment). Managed in the room form only with `rooms.manage` (`RoomController::authorizeImages()` runs *before* anything is saved; `rooms.edit` alone — Réception changing a status — gets a 403 if it sends photos). `RoomRequest` validates real, decodable images (`image`, `mimes:jpg,jpeg,png,webp`, `max:2048` KB, and `dimensions` 50–8000 px so PHP actually parses the header — a renamed script or a decompression bomb fails), the 5-photo total (kept + new) and `remove_images[]` (only the room's own photos are deleted). Deleting a `RoomImage` deletes its file; deleting a `Room` deletes its photos one by one (the FK cascade alone would orphan the files). **PHP here caps uploads at 2 MB/file and 8 MB/request**, so `admin.js` (`[data-image-uploader]`) re-encodes picked photos in the browser to JPEG ≤1600 px (also stripping EXIF/GPS) before upload, with previews, a counter, per-photo removal and a lightbox; it falls back from `createImageBitmap` to an `<img>` decode if the former rejects or stalls >4 s.
- `Guest` — client record (name, phone, email, ID document, nationality, address). **A natural person or a legal entity** (migration `2026_10_10_200000_*`): `type` (`Guest::TYPE_PERSON` « physique », default / `TYPE_COMPANY` « morale »), `company_name` (raison sociale), `tax_id` (RCCM / NCC); for a company first/last name are the contact person (`contactName()`). **Only the phone is required** (client request): names are optional but the columns stay non-null, so an unknown name is stored as `''` (`GuestRequest::guestAttributes()`, which also drops company fields for a person). `fullName()` is the single display name: company name for a company, else the person's name, else « Client sans nom ». Searches (guests list + autocomplete, affectations filter, front-desk search) include `company_name`; the receipt shows a company's RCCM/NCC and contact.
- `Reservation` — belongs to `Guest` + `Room`; **one record per guest file**, whether it's an *affectation* (guest moves in now, room board) or a *réservation* (booked ahead) — see "Affectations and réservations are two separate features" below; `origin` says which. `pricing_mode` (`App\Enums\PricingMode`: heure/journee/nuitee/sejour), `duration` (in that mode's unit: hours / 6 h days / nights / 24 h periods), `check_in`/`check_out` **timestamps**, `status` (`App\Enums\ReservationStatus`: en_attente/confirmee/enregistree/terminee/annulee), `unit_rate` (rate per hour/night/24 h — editable snapshot for discounts/negotiated prices, pre-filled from the room type's rate for the mode, not a live FK), `total_amount`. The `saving` event is the **single source of truth**: `check_out` is always derived via `PricingMode::resolve()` (heure: +N h; journée: +N×6 h; séjour: +N×24 h; nuitée: 12:00 N days after the night it starts — a date-only nuitée starts at 22:00, an arrival before 12:00 belongs to the previous night) and `total_amount = unit_rate × duration` — never trust submitted values for either. An explicit `check_out` is only used to *infer* the duration when none is given (date-based reservations form, factories/tests). When `total_amount` changes on update (stay extended, rate changed), the `updated` event re-bills the invoice (`amount` + `recalculateStatus()`). Existing date-only stays were converted to nuitées by migration `2026_10_07_400000_*` (which renamed `rate_per_night` → `unit_rate`).
- `Invoice` — one-to-one with `Reservation`, auto-created in `Reservation::booted()`'s `created` event (number format `INV-{year}-{seq}`, status `App\Enums\InvoiceStatus`). Numbers come from a per-year counter row in `invoice_sequences`, locked (`lockForUpdate`) inside the same transaction as the invoice insert — **never derive the number from counting invoices**: invoices do get deleted (cascade from deleting a guest/room/room type), which made the old count-based scheme reissue an existing number and crash reservation creation. Issued numbers are never reused, even after deletion. There is deliberately no "create invoice" route/view — invoices only ever originate from a reservation being created (`InvoiceController` only has `index`/`show`). If a new invoice-adjacent feature is added, keep this guard.
- `Payment` — belongs to `Invoice`; `method` is `App\Enums\PaymentMethod` (**especes / orange_money / wave only** — the old mobile_money/carte/virement were retired by migration `2026_10_08_300000_*`). **Mixed payments**: one *encaissement* = one or more Payment rows (one per method, `distinct`) sharing a `settlement` uuid, always recorded through `Invoice::settle($lines, $paidAt, $notes)`, which locks the invoice row and **refuses any total above `remainingAmount()`** (`ValidationException`) — the form requests pre-check the same thing (`Concerns\ValidatesPaymentLines`: `payments[i][method|amount]` — **only the method and amount are recorded**, the client asked for no transaction reference (the `payments.reference` column is left unused); blank lines dropped, legacy single `method/amount` shape still accepted). **Cash lines** carry an optional `received` (what the guest handed over, field "Reçu", shown only for espèces by `admin.js`): `Invoice::settle()` stores `amount_received` (default = the amount) and `change_given` = received − amount, **always computed server-side** (a client-sent change is ignored), refuses received < amount, and leaves both null for Orange Money/Wave; the change is echoed in the flash messages and the invoice history. Deleting a payment (`PaymentController@destroy`) removes its whole settlement. `created`/`deleted` events call `Invoice::recalculateStatus()`, which sums payments against `amount` to flip status between impayee/partiellement_payee/payee. Payments are taken from the invoice page (`PaymentController@store`), as an optional deposit when booking, **or at check-in in the room assignment modal, where an affectation must be paid in full** (`RoomAssignmentRequest`: lines summing exactly to rate × duration — less is refused with "Une affectation se paie en totalité…", more as an overpayment; a 0-FCFA stay needs none; same transaction as the stay). Because of that, `RoomAssignmentRequest::authorize()` requires `payments.create` on top of the route's `affectations.manage`. At the desk (affectation, réservation deposit) the cash amount received is **mandatory** on cash lines (`checkCashReceivedEntered()`); on the invoice page it stays optional (blank = exact amount). In the modal the single line is pre-filled with the stay total until the cashier edits it (`data-full`). The shared Blade partial is `admin/payments/_lines.blade.php` (+ `_line`), driven by `[data-payment-lines]` in `admin.js` (add/remove lines, live encaissé/reste dû summary, "Tout encaisser"). There's no standalone payments list.

The enums in `app/Enums/` (`RoomStatus`, `ReservationStatus`, `InvoiceStatus`, `PaymentMethod`) expose `getLabel(): string` and `getColor(): string` (a **Bootstrap** color token — `success`/`danger`/`warning`/`secondary`/`info`, used directly as `bg-{{ $status->getColor() }}` in Blade for status badges). They no longer implement any Filament contract — don't re-add `Filament\Support\Contracts\HasLabel`/`HasColor` imports to them; that's Filament-panel-era code that would fail to resolve now that the package is removed.

**Discounts ("remises") & locked rates** (client request) — the billed `unit_rate` is **always the room type's rate for the mode, never taken from input**: `RoomAssignmentRequest::unitRate()` (affectations, guest-request validation), `ReservationRequest::unitRate()` (keeps an existing booking's agreed rate while its room and mode don't change, else the type's current rate), and `AffectationRequest` never touches it (extensions keep the check-in rate). The forms show the rate read-only (`.rate-locked`, no `name`). Reductions go through an optional discount on `reservations` (migration `2026_10_10_100000_*`): `discount_type` (`montant` | `pourcentage`, `Reservation::DISCOUNT_*`), `discount_value`, optional `discount_reason`, derived `discount_amount`, and `discount_by`/`discount_at` stamped in the `saving` event (never from input). The `saving` event computes `total_amount = unit_rate × duration − Reservation::discountFor(subtotal, type, value)` (percentage capped at 100 % and rounded to the franc, amount capped at the subtotal; a zero discount clears the type) — so the invoice re-billing, guarantee, payments-in-full, deposits and "not below what's paid" checks all work on the discounted total. Shared validation in `Requests\Admin\Concerns\ValidatesDiscount` (rules, `checkDiscount()` refusing > 100 % or > subtotal, `discountAttributes()`, `totalAfterDiscount()`); fields in `admin/partials/_discount-fields` (board modal, réservation form, guest-request validation, affectation page), live preview in `admin.js` (`discountAmount()`, `discountTooHigh()`, `totalText()`, same rule as the server). Shown on the affectation page (with who granted it), invoice (sous-total/remise), receipt, affectations/réservations lists, and the dashboard (« après X FCFA de remises », `monthlyDiscounts`; billed revenue is net). `discount_value` is in `NormalizeMoneyInputs`. `RoomTypeFactory` now has **fixed** rates (5 000 / 20 000 / 75 000 / 90 000) since tests must know the billed rate.

**Room availability & double-booking prevention** — a room can never be held twice over overlapping periods (date, time or any overlap). **`Room::constrainToConflicts()` is the single definition** of "holds the room over [start, end)", to the minute: **who holds a room** = a stay in progress (`enregistree`) always, and a booking (`en_attente`/`confirmee`) **only once guaranteed, i.e. paid in full** (`reservations.is_guaranteed`, never from input — recomputed by `Reservation::refreshGuarantee()`, called from `Invoice::recalculateStatus()` on every payment/amount change and when the status changes; free bookings count as guaranteed); unpaid/partly paid bookings, cancelled and finished stays never hold it. **A mandatory cleaning time** (`config('hotel.cleaning_buffer_minutes')`, 30 by default, editable in Paramètres, 0 = none) must separate two stays: the requested period is widened by it on both sides. **A stay in progress whose departure time has passed keeps holding the room until its real check-out.** Consequences: unpaid bookings may overlap each other and an affectation or a guaranteed booking may take their slot — they're kept but flagged (`Reservation::takenBy()`, "Non garantie · chambre prise" in the list/page), their arrival is refused while taken (`ReservationController@checkIn` runs `lockAvailable`), and **the first booking paid in full wins**: `Invoice::settle()` refuses the payment that would fully pay a booking whose slot is already held (deposits stay possible). `Room::conflictMessage($conflict, $start, $end)` explains overlaps, the cleaning gap ("libérée le … ; au plus tôt le …" / "doit se terminer au plus tard le …") and overdue stays. It backs `scopeAvailableBetween()`, `conflictingReservation()` (the first conflict, for precise messages built by `Room::conflictMessage()` — dates, or "encore occupée… faites le check-out") and **`Room::lockAvailable($roomId, $start, $end, $excludeId, $errorKey)`**, which locks the room row (`lockForUpdate`) and re-checks inside the transaction, throwing a `ValidationException`. Every write path calls it right before writing, inside `DB::transaction()`: `RoomAssignmentController@store` (also re-checks the room is still `disponible`), `ReservationController@store`/`@update`, `AffectationController@update` — so two simultaneous requests are serialised and the second one is refused (`OverlapProtectionTest` simulates it via `afterResolving` on the FormRequest; a mutation check confirmed the test fails without the lock). The FormRequests (`RoomIsAvailableForDates` rule in `ReservationRequest`, `AffectationRequest`) and the assignment pre-check use `conflictingReservation()` for early, precise feedback. Under all that, **PostgreSQL enforces it too**: exclusion constraint `reservations_no_overlap` (`btree_gist`, `tsrange(check_in, check_out, '[)')` per `room_id`, restricted to holding rows: `status = 'enregistree' OR (status IN ('en_attente','confirmee') AND is_guaranteed)` — migrations `2026_10_08_900000_*` / `950000_*`, skipped on SQLite; the cleaning buffer and overdue rule are application-level only); a violation (SQLSTATE 23P01) is turned into a friendly validation-style redirect in `bootstrap/app.php`. A room **hors service can't be booked** (`ReservationRequest`) and isn't offered by `/admin/rooms/available`. (`/admin/rooms/available` is the JSON endpoint behind the réservation form's room list; the room board offers only `isAvailableNow()` rooms.)

**Reservation status transitions drive room status** — `Reservation::booted()`'s `updated` event: status → `enregistree` (check-in) sets the room to `occupee`; status → `terminee` (check-out) **or** → `annulee` from `enregistree` (cancelling a stay in progress) sets it straight back to **`disponible`** (client request, 2026-10-08: no automatic cleaning step) — but only if the room is still `occupee`, so a room put hors service meanwhile stays so; a booking cancelled before arrival never touches the room. `nettoyage` is now only set by hand (room edit); the one-click **"Chambre prête"** action (`RoomController@markReady`, `POST /admin/rooms/{room}/ready`, `rooms.edit`, only from `nettoyage`) still brings such a room back to `disponible`. In the UI, check-in (`ReservationController@checkIn`, "Arrivée du client"), check-out (`AffectationController@checkOut`) and cancel (on either side) are dedicated one-click POST actions rather than a generic status dropdown — they flip `status` and let the model event cascade.

**"Réservée" is a computed state, not a `RoomStatus`** — a `confirmee`/`en_attente` reservation (reservations module: a future booking) leaves `rooms.status` at `disponible` until check-in (status stays the room's *physical* state; flipping it at assignment would wrongly block rooms booked for a later date). `Room::pendingArrival()` (a **guaranteed** en_attente/confirmee booking starting by the end of today and not yet over; an unpaid one for today only shows a "Réservation non soldée aujourd'hui" notice on the free card via `unguaranteedArrival()`, the room stays assignable) drives it: `scopeAvailableNow()`/`isAvailableNow()` = disponible **and** no pending arrival (what the board makes clickable and the dashboard counts as available), `scopeReservedNow()`/`isReserved()` = disponible **with** one (shown as an info-colored "Réservée" badge/card). `Room::nextArrival()` shows "Réservée à partir du …" on free rooms booked later. Any new "free rooms" query should use `availableNow()`, not `where('status', 'disponible')`.

**Rooms are always shown grouped by state** in the order of `Room::DISPLAY_STATES` (Occupées → Libres → Réservées → En nettoyage → Hors service, with label and color — the single source for the board sections, the room list's filter pills and group header rows, and the dashboard legend), then naturally by number (`Room::sortForDisplay()`, `displayState()`). Because "réservée" is computed, the room list sorts in PHP and paginates by hand (`LengthAwarePaginator`, 20 per page). On the board each state is a **tab** (`[data-room-tabs]` buttons + `[data-room-panel]` sections, `admin.js`): one panel at a time, opening on the URL hash (`#disponible`, `#occupee`…) if valid, else the state of a room whose assignment just failed, else "Libres", else the first non-empty state; empty states have a disabled tab and no panel; the active tab is written back to the hash so reloads keep it. Without JS every section shows (headings hidden only once `room-tabs-ready` is set). Occupied cards show the stay's entry/exit times (`currentStay`) but **never the guest's name** (client request). In the **« Libres » panel the free rooms are grouped by room type** (client request, 2026-10-11): one `.room-type-heading` per type (name, « N libres », « dès X F / unité » = its cheapest formula), types in natural name order, rooms in natural number order inside; the other panels stay one grid (`BoardByTypeTest`).

**Room list (`/admin/rooms`) filters by status** (`?status=occupee` etc., plus the pseudo-status `?status=reservee`; pills with per-status counts; unknown values ignored via `RoomStatus::tryFrom`). For occupied rooms it shows the stay's entry and exit times through `Room::currentStay()` (the room's `enregistree` reservation) but **not the guest's name** (client request — the Client column is dropped on the "Occupées" tab and left empty for occupied rows elsewhere); reserved rooms still show the arriving guest. These columns are behind `@can('reservations.view')`.

**Room board (`/admin/rooms/board`) is the "affectation" screen** (guest moves in now) — a grid of room cards (`resources/views/admin/rooms/board.blade.php`), colored by `RoomStatus::getColor()`. Only rooms that are `isAvailableNow()` carry `data-assign-room` and are clickable; clicking one opens a single shared Bootstrap modal (`#assignRoomModal`) set up by `public/app/js/admin.js` from the card's `data-*` attributes, including `data-hourly-rate`/`data-day-rate`/`data-night-rate`/`data-stay-rate` (empty = mode not offered → its radio is disabled; nuitée is also disabled before 22:00). The modal lets staff either search an existing guest (`GET /admin/guests/search`, a small fetch-based autocomplete — see `data-guest-search` wiring in `admin.js`) or fill 3 quick fields to create one inline — **all optional** (client request): whatever is typed is kept, and with no name at all `RoomAssignmentController::createGuest()` creates a per-stay guest named `Guest::WALK_IN_FIRST_NAME`/`WALK_IN_LAST_NAME` (« Client de passage », empty phone) to complete later; réservations still require a guest — then pick **mode + duration + rate** (pre-filled from the type, editable) with a live departure/total preview (JS mirror of `PricingMode`, display only). There is **no arrival field**: `RoomAssignmentRequest::arrival()` is the server's current time. `RoomAssignmentRequest` refuses a mode the room type has no rate for and a nuitée outside its window (`PricingMode::canStartAt`, from 22:00 until 12:00); `RoomAssignmentController@store` refuses rooms that aren't physically `disponible`, checks availability for the resolved period, then — in one transaction — creates the `Guest` (if new) and the stay, and immediately checks it in (`enregistree`, same path as `ReservationController@checkIn`, so the model event flips the room to `occupee`). Future bookings belong to the reservations module, not the board. **Modal layout** (client request, 2026-10-11): left column Client then Séjour (mode, duration, occupants, locked rate); right column a **« Règlement »** block (`.assign-pay`): the total to pay (`[data-stay-preview]`, `.assign-pay__total`), the encaissement lines (method + amount), and **right under « Ajouter un mode »** the discount and a single « Montant reçu du client » with the change (client request). `_lines` takes `sharedReceived` (one shared `[data-received-shared]` field — there is at most one cash line since methods are distinct — that admin.js copies into the cash line's hidden `payments[i][received]`; posted data and server rules unchanged) and `afterActions` (HTML rendered under the actions, here the discount partial via `view(...)->render()`). The invoice page keeps one « Reçu du client » per cash line. `data-stay-form` now sits on the row spanning both columns (admin.js looks the stay fields and the preview up inside it). The guest-request validation page and the réservation form (deposit, create only — without deposit the discount shows alone) use the same `.assign-pay` block and order (`PaymentFormLayoutTest`). **A failed submission reopens the modal**: the form posts a hidden `assign_room_id`; on the redirect back, `board.blade.php` sets `data-reopen-room` when that room is still `isAvailableNow()`, and `admin.js` reopens it via `openAssignModal(card, restore = true)`, which keeps every old value (client fields, `guest_id`/`guest_label`, mode, duration, negotiated rate, payment lines) instead of resetting them. Client-field errors render inline (`is-invalid` + `invalid-feedback`), others in a `data-modal-errors` list at the top of the modal; the view then defines section `inline-errors`, which makes the layout skip its page-level `data-page-errors` alert (shown as usual when the room can't be reopened). That view uses inline `@php(...)` — keep it that way (no `@php … @endphp` blocks there). **Phones**: the modal is `modal-fullscreen-sm-down`, and because its header/body/footer sit inside a `<form class="modal-form">` (not directly in `.modal-content`), `admin.css` makes that form a flex column so Bootstrap's scrollable body works — without it the overflow is clipped and the lower fields/submit can't be reached. Any new modal wrapping its parts in a form needs the same `modal-form` class.

**Prices on the room board** (client request: inform guests at the desk) — free cards (`isAvailableNow()` only, never occupied/reserved/requested ones) list every formula their room type offers with its price (`.room-card__rates`; a closed nuitée is still listed with « dès 22h00 »), and a folded **« Grille tarifaire »** `<details data-rate-grid>` at the top of the board shows one row per **active** room type offering at least one formula (four rate columns, « — » when not offered, capacity, and how many of its rooms are free now — `RoomController@board`'s `$rateGrid`). **Affectations and réservations are two separate features** (client requirement — never mix them in the UI). A réservation whose guest arrived is therefore in both lists — as the stay on the affectations side, as "Honorée (client arrivé)" in the réservations history (`ReservationStatus::reservationLabel()` / `affectationLabel()` give each side its wording).

Blade components `<x-admin::file-badge :file=… :reference :link />` (amber + key « AFFECTATION » / blue + calendar « RÉSERVATION », colours `--ek-stay` / `--ek-booking`) and `<x-admin::kind-icon kind=… />` (page titles). - **Affectations** (`AffectationController`, `/admin/affectations`, menu "Affectations", permissions `affectations.view|manage|cancel`): created from the room board (`RoomAssignmentController`, sets origin affectation) or by a réservation's check-in; list tabs En cours / Terminées / Annulées / Toutes, with a GET filter bar (`AffectationController::filters()` sanitises every value and silently ignores unknown ones: client search on first/last/full name — case-insensitive via `lower()` — or phone, entry period by business day incl. custom range, room, room type, mode, invoice status, origin directe/sur réservation, overdue only, sort) applied to the rows, to the tab counts and to the totals strip (count, billed, cashed, due — computed over the whole filtered set, not just the page); each row shows room+type, guest+phone, mode+billing, entry/exit (overdue badge), occupants, billed/cashed/remaining + invoice status/number, status + origin; the show page extends/shortens the stay (`AffectationRequest`: duration, rate, occupants, notes — refused if it would overlap another booking or drop below what's already paid), check-out, cancel. Every action 404s on files that aren't stays.
- **Réservations** (`ReservationController`, `/admin/reservations`, permissions `reservations.view|manage|cancel`): the client is picked with the guest autocomplete (`guest_id`) **or entered inline** — `new_client_type` (particulier / entreprise, `[data-client-form]` toggle in `admin.js`), `new_phone` (**the only required field**, `required_without:guest_id`), optional `new_first_name`/`new_last_name`/`new_company_name`/`new_tax_id` — created by `ReservationRequest::resolveGuestId()` inside the write transaction (store and update, so a booking's client can be switched); booked ahead in **any of the four modes** (form `[data-booking-form]` in `admin.js`: arrival is a date for a nuitée, date+time otherwise; live departure/total preview; room list from `/admin/rooms/available`); `ReservationRequest` refuses an arrival now/in the past (that's an affectation), a mode the room type has no rate for, a status other than en_attente/confirmee, and (on update) a total below the deposit; the legacy date-based shape (check_in → check_out) is still accepted. The invoice is created at booking; an optional **deposit** (`payments[...]`, same partial and `Invoice::settle()` as elsewhere, needs `payments.create`) can be taken in the same transaction. **Check-in = "Arrivée du client"**: only for en_attente/confirmee bookings whose period isn't over and whose room is physically `disponible`; flips to enregistree (room → occupee) and redirects to the affectation. A no-show is left to the manager: cancel, or edit to postpone ("reporter"). Editing a started booking redirects to its affectation.

**Business day ("journée commerciale") & manager-editable settings** — the hotel's day runs from `config('hotel.business_day_start')` (06:00 by default) to one minute before it the next day (05:59). `App\Support\BusinessDay` (`dateOf()`, `today()`, `bounds()`/`current()` as `[start, end)`, `monthBounds()`, `contains()`) is the only place that knows this; use it — not `today()`/`whereDate()`/`whereMonth()` — for anything "of the day/month": the dashboard's today's arrivals/departures, monthly revenue and upcoming arrivals, `Room::pendingArrival()`/`nextArrival()` ("Réservée" for the current business day), the rooms list "Aujourd'hui" departure badge, and **invoices** (`issued_at` = business date; `Invoice::generateNumber()` uses the business-day year, so Jan 1 at 03:00 is numbered on the previous year). Real check-in/check-out timestamps, availability and the pricing-mode maths are unaffected. The business-day start, the pricing windows (`night.from`/`night.until`, `day_hours`, `stay_min_hours`) and the cleaning time (`cleaning_buffer_minutes`) are editable in **Configuration → Paramètres** (`SettingsController`, `settings.manage` permission): stored in the `settings` key/value table and layered over `config/hotel.php` at boot by `App\Support\HotelSettings::apply()` (cached forever under `hotel.settings`, flushed on save; falls back to the file defaults when the table doesn't exist yet), so the rest of the code keeps reading `config('hotel.*')`. `SettingsRequest` requires the night window to span midnight (start after the departure time) because `PricingMode` assumes it.

**Checkout alarm** — when a checked-in stay's `check_out` is reached, staff with the `alerts.checkout` permission (Gérant via the system role; assignable to other roles) get an in-app alarm on every admin page: the layout renders `#checkoutAlerts` only `@can('alerts.checkout')`, and `admin.js` polls `GET /admin/alertes/departs` (`CheckoutAlertController@index`, backed by `Reservation::scopeOverdueCheckouts()`) every 30 s, shows one card per stay (room, type, guest + phone, mode, billing, arrival, planned departure, minutes overdue — built with `textContent`, never `innerHTML`), rings a Web Audio beep on each poll while alerts remain, and prefixes the tab title with the count. "Vu" posts to `.../{reservation}/vu`, which sets `overdue_acknowledged_at/_by` (silences it for everyone); checking out also clears it, and a changed `check_out` (stay extended) re-arms it in the `saving` event. Browsers only allow sound after a user gesture, so audio is unlocked on the first click/keypress (an "activer le son" button appears otherwise). The "Ouvrir (check-out)" link is only sent to users with `reservations.manage`. Note the polling keeps the session alive while a tab stays open. Adding `?demo-alarme` to any admin URL renders a client-side sample alarm (no DB write, polling paused on that page) — for showing the feature without creating a fake stay (which would burn an invoice number).

**Controllers/routes/views pattern** (`app/Http/Controllers/Admin/`, `app/Http/Requests/Admin/`, `resources/views/admin/`) — plain resourceful CRUD per entity (`RoomTypeController`, `RoomController`, `GuestController`, `ReservationController`), each with a dedicated `FormRequest` and an `index`/`create`/`edit` Blade view sharing one `_form.blade.php` partial included from both `create` and `edit`. No Livewire, no Inertia, no reactive components — forms `POST`/`PUT` normally and the page reloads; the only client-side JS is the room board modal, the reservation form's dynamic room `<select>`, and the guest-search autocomplete (all in the single `public/app/js/admin.js`, vanilla, no build step). Routes are registered via `Route::resource(...)->except([...])` in `routes/admin.php` plus a handful of manual routes for the non-CRUD actions (board, assign, search, available, check-in/out/cancel, payments).

**Language is French throughout** — `APP_LOCALE=fr`. UI strings in both halves are hardcoded French in the Blade views (no `__()` calls); `lang/fr/` + `lang/fr.json` exist only so framework-generated text (validation errors, pagination, auth messages) comes out in French too. Keep new UI copy and enum labels in French.

**Staff accounts, roles & permissions** — permissions are defined **in code** (`App\Enums\Permission`, values like `rooms.view`, `payments.delete`); roles are **in the database** (`roles` table + `permission_role` pivot of permission strings, migration `2026_10_07_100000_*`), one role per user (`users.role_id`). `AppServiceProvider::boot()` registers one `Gate` ability per enum case (deny by default), so authorization is enforced with `can:<permission>` route middleware in `routes/admin.php` — controllers and their `FormRequest::authorize()` stay permission-agnostic — and mirrored in Blade with `@can` purely to hide unusable buttons/menu items. **Every new admin route must get a `can:` middleware**: `PermissionTest::test_every_admin_route_requires_a_permission` fails otherwise (dashboard/profile/login/logout are the only whitelisted exceptions). A role with `is_system = true` (the seeded "Gérant") implicitly holds *every* permission, including ones added to the enum later, and can't be edited or deleted. Adding a permission = add an enum case (+ label/group) and reference it on routes; it then appears as a checkbox in the role form automatically.
- Privilege-escalation rules live on `User` (`canGrantPermissions`/`canGrantRole`/`canManageUser`) and `RoleRequest::actorCanEdit`: you can only hand out a role/permission set you fully hold yourself, can't edit your own account through `/admin/users` nor your own role, and can't touch accounts/roles that outrank you. `role_id`/`is_active`/`must_change_password` (users) and `is_system` (roles) are intentionally **not** in `$fillable` — set them explicitly after authorization.
- `App\Http\Middleware\EnsureStaffAccountIsUsable` (on the whole authenticated admin group) logs out accounts deactivated mid-session and confines `must_change_password` accounts (every account created or password-reset by someone else) to `/admin/profil` until they pick a new password. `User::logoutEverywhere()` deletes the user's DB sessions and rotates the remember token — called on password change and on role/status/password changes made by an admin. Password policy is `Password::defaults()` = **at least 4 characters, nothing else** (client request), set in `AppServiceProvider`.
- Staff are deactivated, never deleted (no `destroy` route on users) — keeps history intact.
- **« Mon profil »** (`ProfileController@update`, `PUT /admin/profil`, unguarded like the rest of the profile — whitelisted in `PermissionTest`; temporary-password accounts are still confined to the password form by `EnsureStaffAccountIsUsable`): each staff member edits their own **name and login e-mail** (`ProfileUpdateRequest`: unique e-mail; changing it requires the current password in `confirm_password` and logs the account out of its other sessions). Role, status and password reset stay in Personnel (`UserController`).

**Authorship** — `App\Models\Concerns\RecordsCreator` stamps `created_by` (= `Auth::id()`, never from input — not fillable) on `Reservation`, `Payment` and `Guest` when created (relation `creator()`); `Reservation`'s `saving` event also stamps `checked_in_by/at`, `checked_out_by/at`, `cancelled_by/at` whenever `status` changes to enregistree / terminee / annulee (relations `checkedInBy()`, `checkedOutBy()`, `cancelledBy()`). Shown on the affectation page ("Historique" trail), the affectations/réservations lists ("par …"), the réservation page and the invoice payment history. Rows created before migration `2026_10_08_500000_*` (or outside a request) show "—". This is per-record authorship, not a full activity log.

**Financial history can't be deleted away** — a `Guest` or a `Room` that has any stay/booking, and a `RoomType` that still has rooms, refuse deletion: their `deleting` events throw `App\Exceptions\DeletionBlocked` (message shown as is; `GuestController`/`RoomController`/`RoomTypeController@destroy` catch it and redirect back with an error), and under that the DB foreign keys `reservations.guest_id`, `reservations.room_id` and `rooms.room_type_id` are `RESTRICT` (migration `2026_10_08_800000_*`; they used to `CASCADE`, which silently wiped stays, invoices and payments). The way out for a room is "Hors service", for a type "Type actif" unticked. Stays themselves have no delete route.

**Amount inputs use thousands separators** (client request) — every money field (`unit_rate` in the board modal / réservation form / affectation page / guest-request validation, the four room-type rates, `payments[i][amount|received]`) is `type="text" inputmode="numeric" data-money`, rendered with `number_format(…, 0, ',', ' ')`. `admin.js` groups digits while typing (capture-phase `input` listener, caret kept) and **must read/write them through `moneyValue(input)` / `setMoney(input, n)`** — a raw `parseFloat("15 000")` gives 15. Server side, `App\Http\Middleware\NormalizeMoneyInputs` (on the authenticated admin group) strips regular/non-breaking/narrow spaces from those keys before validation, so requests without JS work too and form requests keep seeing plain numbers. Displayed amounts were already grouped (`$fcfa`/`number_format`). New money field = add `data-money`, its key to the middleware regex, and use the JS helpers.

**Tables become cards on phones** (client request, 2026-10-11) — a block at the end of `admin.js` adds `.table-cards` to every `<table>` with a `<thead>` inside `.admin-content` (except `.table-keep` and the « Voir les données » twins in `<details>`/`.dash-data`) and copies each column's header into its cells' `data-label`. Under 768 px (`admin.css`, « Tables as cards on phones ») each row is a card: label left / value right, the **title cell** on top in bold (first column, or the `<th data-card-title>` one — e.g. « Montant » on Recettes), the « Actions » / unlabelled last column as full-width buttons side by side at the bottom, cells holding only « — » hidden, a single wide cell (group heading, empty state) spanning the card, and the wrapping `.admin-card` made transparent. Desktop/tablet are unchanged and, without JS, tables still scroll sideways. New tables get it for free; give a secondary column `class="cell-hide-sm"` to drop it on phones. Tests assert exact cells like `<td>101</td>` on the room list, so keep markup changes for mobile in CSS/JS.

**SweetAlert pop-ups (opt-in per page)** — SweetAlert2 11.14.5 is vendored in `public/vendor/sweetalert2/` (no CDN at runtime). **Mode simple / Mode complet (per account)** — `users.ui_mode` (`simple` default for every account incl. existing ones, `complet`; migration `2026_10_09_300000_*`), `User::usesSimpleUi()`, switched by the topbar button (`POST /admin/mode`, `UiModeController`, unguarded like the profile — whitelisted in `PermissionTest`). **« Recettes » (`Admin\RevenueController`, `/admin/recettes`, menu « Recettes », `payments.create`)** — payments actually received over a period, one line per payment: date/time, file (badge + room + invoice), client, method, amount, received/change, **Encaissé par** (`payments.created_by`) and **Affecté par** (`Reservation::assignedBy()`: whoever checked the stay in — board assignment, validated guest request or a réservation's arrival — else the affectation's creator; a booking whose guest hasn't arrived shows « Réservation (client pas encore arrivé) »). **Guest requests ("Demandes clients", `stay_requests` table, `App\Models\StayRequest`)** — a request from `/demande` is **not** a reservation row (no invoice, may never become a stay).
